## 一句话抓住全文

**Agent 评测的价值，是让系统持续变得可靠，并把失败变成具体修复。**

全文十章都围绕同一个循环：

```text
定义业务验收 → 设计用例 → 执行并记录过程 → 判断是否通过
→ 定位原因并修复 → 回归验证与上线 → 收集线上失败 → 更新用例
```

## 1. 答案正确，只证明了一部分质量

Agent 会选择工具、规划步骤、改变系统状态。要把最终回复、执行轨迹和真实业务状态一起看。

| 检查对象 | 核心问题 |
| --- | --- |
| Turn：单轮 | 当前回复是否正确、相关、完整？ |
| Session：整段会话 | 多轮交流最终解决问题了吗？ |
| Trace：执行轨迹 | 工具、参数、调用顺序和异常处理是否正确？ |
| Outcome：最终结果 | 任务是否达成，实际状态是否符合预期？ |

例如，Agent 回复“退款成功”，但没有调用退款工具、业务状态也没变化，仍然失败。客服每轮都很礼貌，但聊了十轮仍没解决问题，整段会话的任务完成指标也应该判失败。

## 2. 指标服务业务，优先级要分清

先分清 Agent 类型：知识问答关注准确性与证据，任务执行关注工具和状态变化，多轮引导关注记忆、澄清与目标推进。评测执行骨架可以复用，验收标准必须结合业务设计。

| 维度 | 记忆问句 | 文章建议的优先级 |
| --- | --- | --- |
| 功能正确性 | 做对了吗？ | P0 |
| 稳定性与安全 | 会出严重问题吗？ | P0 |
| 过程质量 | 路径合理吗？ | P1 |
| 效率与成本 | 划算吗？ | P1 |
| 体验与对齐 | 用户感受好吗？ | P2 |

P0 用于发布门禁，P1 支持版本优化，P2 关注体验改善；实际优先级仍需结合业务调整。

重复运行时，区分两种观察口径：

- **至少一次成功**：多次运行中有一次成功，说明具备完成任务的可能。
- **全部运行成功**：多次运行每次成功，提供更强的稳定性证据。

有限次数全部通过，不能保证未来每次成功。版本比较还要结合置信区间、显著性判断和预先定义的变化阈值，避免把随机波动误认为能力提升。

## 3. 好评测集要主动覆盖容易失败的地方

只随机抽线上对话，常见的简单场景容易占多数，高风险边界可能被漏掉。

文章建议先建立 **50～200 条高质量核心用例（Golden Set）**。数量是起步参考，覆盖和验收标准更重要。

- 专家设计用例：定义期望行为和业务标准。
- 受规则约束的扩展用例：扩展用户表达、状态和情绪组合。
- 真实线上样本：覆盖实际使用分布。
- 错例回流：将确认过的失败变成回归用例。

退款场景不能只测“我要退款”，还要覆盖订单已发货、订单号缺失、查询工具超时、用户中途换订单等情况。

**用例必须明确期望行为。**“回答合理”太模糊；“先查询订单状态，再按规则处理”才容易检验。

Skill 用例可以按四类组织：该不该触发、核心流程对不对、产物能不能用、异常时能不能稳住。

## 4. 评分器也会犯错，需要分工和校准

| 谁来判断 | 适合判断什么 |
| --- | --- |
| 代码／规则 | 是否调用工具、参数是否正确、状态是否变化、是否违反硬规则 |
| LLM Judge：模型裁判 | 解释是否完整、是否理解意图、策略是否合理 |
| 人工 | 业务口径不明确、自动结论冲突、高风险样本和裁判校准 |

**能明确写成代码的检查，优先用规则。**模型裁判需要具体分档、边界示例、判定依据和定期校准，不能只写“请从 1 到 5 打分”。

文章提到的“约 85% 人工一致率”是参考值，不能直接当成所有业务的统一门槛。还需要关注高风险漏判和边界样本的重复评分稳定性。

评分输出应包含通过与否、问题现象、置信度和依据，为后续归因提供入口。

## 5. 判出失败，还要找到原因并完成修复

| 层次 | 退款案例 |
| --- | --- |
| 现象：用户看到了什么问题？ | Agent 无依据地承诺可以退款 |
| 过程：哪一步偏离要求？ | 跳过订单状态查询 |
| 根因与责任：为什么出错、由谁修？ | 结合 Trace 确认，例如流程缺少查询前置约束 |

“过度承诺”是现象，不能仅凭它就认定是 Prompt 的问题。先收集证据，再缩小候选模块范围，最后判断责任和修复动作。

有效行动项至少包含：**失败范围、证据、具体动作、负责人、优先级、验收方式**。

例如，若确认流程缺少约束，就补上订单状态查询前置条件，明确负责人，并重跑相关场景和同类回归用例。修复后继续观察线上任务完成率、重复追问率、转人工率与投诉变化；离线分数提高但线上效果恶化时，应调查并考虑降级或回滚。

## 阅读顺序与项目应用

第一遍优先理解原文第 **4～7 章：指标 → 用例 → 评分 → 归因**，再接上第 9 章的持续反馈。复杂的多 Agent 分析流水线、看板和平台模块可以等基础闭环运转后再展开。

应用到 LumenMind-pi 时，先定义实际业务能力下的成功标准，再检查回复、Trace 和会话结果。本文是方法论阅读笔记；项目当前的接口、运行命令、实现范围和限制，以[评测操作指南](../guides/EVALUATION.md)及相关验收记录为准。
