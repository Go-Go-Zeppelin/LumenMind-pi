# 《Anthropic 这套 Agent 评测体系，太牛了》速览

五分钟阅读笔记，重点理解怎样定义成功、设计可执行的评测任务，以及验证可靠性。

- [本地原文](../references/Anthropic%20这套%20Agent%20评测体系，太牛了.md)
- [微信来源](https://mp.weixin.qq.com/s/J8vNXosm1a2meqeLCGIafw)

这是一篇对 Anthropic《Demystifying evals for AI agents》的阅读解读，包含文章作者自己的六层框架。下面按所提供文章总结，没有将其视为 Anthropic 官方原文，也未独立核验一手资料。

## 一句话抓住全文

**先证明任务真的完成，再理解它是怎么完成的；对结果严格，对合法路径宽容。**

与[《Agent 评测：方法论与体系设计》](agent-evaluation-methodology-summary.md)相比，这篇最值得补充的是：环境终态、合法替代路径、幂等与重试、干净环境，以及能力集和回归集的分工。

## 1. Outcome 和 Transcript 解决不同问题

| 对象 | 含义 | 核心问题 |
| --- | --- | --- |
| Outcome：真实结果 | 任务结束后的实际状态 | 事情办成了吗？ |
| Transcript：执行记录 | 回复、工具调用、参数、中间结果、重试 | 为什么成功或失败？ |

退款落库、生成文件、代码可运行等结果，优先用数据库查询、文件检查和测试验证，再结合执行记录检查参数、权限和重试过程。

一个典型风险是：**退款已经成功，工具却返回超时，Agent 直接重试，造成重复退款。**

这个例子说明，要测的不只是“能否恢复”，还包括“恢复时是否先确认真实状态、是否保持幂等”。最终成功也不能掩盖重复操作或不相关数据被修改。

## 2. 验收必要约束，允许合法替代路径

不要因为设计者预想了 A→B→C，就把它当作唯一正确轨迹。Agent 可能找到同样满足业务目标、权限、安全和成本要求的其他路径。

| 应明确检查的约束 | 不宜随意固定的细节 |
| --- | --- |
| 身份验证、审批、权限、隐私、资金安全 | 非必要的工具顺序 |
| 必须满足的状态前置条件 | 与正确性无关的步骤数量 |
| 结果正确、相关状态不受损 | 参考解法的每一步和固定措辞 |

**参考解法的作用是证明任务可解、环境和评分器可用，不是限制 Agent 只能照着做。**

如果强模型反复尝试仍然全失败，也要排查任务描述、隐藏要求、环境和 Grader，不能直接认定为模型能力不足。

## 3. 三类 Grader 分工，风险设置硬门槛

Grader 就是评分器或验收器。

| 类型 | 适合判断什么 |
| --- | --- |
| 代码评分 | 数据库终态、文件、可运行代码、工具参数、资源消耗 |
| 模型评分 | 完整性、证据支撑、关键事实、沟通质量 |
| 人工评分 | 高风险、复杂边界、业务口径、模型裁判校准 |

不要让一个模型同时判断所有维度，再用综合均分掩盖硬错误。未经授权的高金额退款，即使表达礼貌、解释完整，也不能总体合格。

证据不足时，应允许模型裁判返回“无法判断”，再进入补证或人工复核，而不是强行猜分。

## 4. 一次成功与重复可靠性不同

| 指标 | 关注点 | 更适合的场景 |
| --- | --- | --- |
| `pass@k` | k 次中至少成功一次 | 允许产生多个候选，再选择可用方案 |
| `pass^k` | k 次全部成功 | 需要稳定执行的配置变更、资金或发布流程 |

文章举例：单次成功率为 75%，三次全部成功的概率约为 42%。

补充理解：**这个计算使用独立、同分布假设**，即 `0.75³ ≈ 42.2%`；共享状态、缓存、环境波动和用户差异都可能破坏这个假设。真实评测要在明确条件下重复运行，并报告样本量与不确定性，不能把演示算式当成线上保证。

## 5. 第一套 Eval 从少量真实任务开始

文章转述的起步建议是 20～50 条真实任务，可从手工发布检查、Bug、支持工单、投诉和生产错例中收集。重点是验收清楚、可重复运行。

每条任务至少写明：

1. 初始状态和用户目标。
2. 允许的工具、禁止的动作、必须审批或转人工的条件。
3. 预期终态，以及哪些状态不能改变。
4. 如何判断通过或失败。

再准备能通过验收的参考解法，检查任务与评分器自身是否合理。

每次 Trial，即一次独立试跑，应从干净环境开始。文件、缓存、Git 历史、数据库记录和多轮状态都可能污染结果。只换一个会话 ID，不等于隔离了所有环境状态。

## 6. 能力集与回归集分开维护

| 数据集 | 要回答的问题 | 维护方式 |
| --- | --- | --- |
| Capability Eval：能力集 | 现在能做到什么，还有哪些难题？ | 可以保留暂时做不好的挑战任务 |
| Regression Eval：回归集 | 以前稳定会做的事情有没有退化？ | 保留已稳定通过、期望行为明确的任务，追求接近全通过 |

挑战任务稳定通过后，可以进入回归集。线上错例也应经确认和整理后持续补充，不能把含糊、环境损坏或不可解释的失败直接当成标准答案。

20～50 条的起步建议与另一篇文章的 50～200 条并不构成统一配额；不同阶段都应优先看覆盖、风险与标准质量。

## 作者整理的六层框架

**以下 L0～L5 是该解读文章作者的整理，不应直接称作 Anthropic 官方六层标准。**

| 层次 | 测试重点 | 典型问题 |
| --- | --- | --- |
| L0 风险契约 | 可访问资源、审批、禁止动作、停止条件 | 未经授权执行操作 |
| L1 单步决策 | 工具选择、参数、澄清、拒绝、转人工 | 填错工具参数 |
| L2 组件与状态 | 检索、记忆、幂等、重试、多轮状态 | 超时重试导致重复退款 |
| L3 端到端任务 | 目标完成、预期终态、无关状态保护 | 回复成功但没有落库 |
| L4 可靠性与安全 | 重复运行、故障恢复、注入、越权和泄露 | 同任务时好时坏 |
| L5 生产效果 | 解决率、接管率、成功成本、延迟和反馈 | 离线高分但用户不满意 |

第一遍记住各层回答的问题即可，不必背编号。

## 线上反馈与项目启发

自动 Eval 支持版本回归；生产监控发现真实流量变化；A/B 比较版本效果；用户反馈暴露漏测问题；人工阅读执行记录帮助解释原因。这些方法需要配合，离线通过不能代替线上验证。

对 LumenMind-pi 的后续启发是：用实际状态定义成功，检查执行记录中的必要约束；给重试补上状态确认与幂等场景；区分能力集和回归集；复核工具顺序要求是否确有业务依赖。以上属于阅读建议，本轮只新增笔记，不改变运行时或评测规则。
